## 2026-09-07 — Azure DevOps + Linux VM/ACA root-cause research

* **Official contract**: Microsoft documents Azure DevOps approvals as resource-owner checks outside YAML, deployment jobs as lifecycle hooks with separate deploy/route/post-route/failure boundaries, ACA readiness before multiple-revision traffic, blue-green labels/weights for rollback, and Linux Custom Script Extension idempotence, protected managed-identity downloads, and agent/handler logs.

* **Root-cause conclusion**: the primary systemic defect is not gate count alone. Source/artifact handoff, foundation mutation, workload what-if, ACA revision/traffic, VM worker readiness, and durable evidence were coupled into one broad mutation task. * **Knowledge graph**: [`docs/research/2026-09-07-azure-devops-linux-vm-root-cause.md`](../../research/2026-09-07-azure-devops-linux-vm-root-cause.md) records the graph, official URLs with observed sections/line ranges, repository file/line evidence, confirmed versus unverified causes, and a staged redesign. * **Toolchain note**: local `az` was not installed, so local CLI help could not be verified. Run 32 hosted evidence recorded Azure CLI `2.89.1`, Azure DevOps extension `1.0.7`, and Bicep `0.46.1`. No Azure mutation or version bump was performed.
* **Status**: `RELEASE_BLOCKED`; no allowlist widening, new Azure run, Teams completion message, or Jira Done transition is justified until artifact read-back and a fresh non-empty failure receipt are proven.

## 2026-09-07 — Run 38/39 worker Blob metadata query root cause and correction

* **Official contract**: Microsoft Azure CLI registers `az storage blob metadata show` against `get_blob_properties` and transforms the result to `x.metadata`, so the command output is the user-defined metadata map at the top level. The current CLI reference defines `metadata show`, `metadata update`, `upload`, `--auth-mode login`, and `--overwrite` as supported Blob operations. Sources: [Azure CLI Storage command registration](https://github.com/Azure/azure-cli/blob/dev/src/azure-cli/azure/cli/command_modules/storage/commands.py), lines 2688-2693, and [`az storage blob`](https://learn.microsoft.com/en-us/cli/azure/storage/blob?view=azure-cli-latest).
* **Observed evidence**: Run 38 / build `20260906.17` failed at `worker-blob` with a retained 533-byte receipt. Run 39 / build `20260906.18`, source `6edcdbc6576ae9585f43ca6dc4fd2241262cc78e`, reached the same boundary and logged `immutable Blob metadata SHA-256 mismatch: expected fe36475c64b74a39876df0734569ad9f880089f37413299035f783598cddc74b, observed <empty>`; its receipt checksum was `623364b369407c354bf013ed942680ea48754b21ac454b40f3a4be9e72731e55`.
* **Classification**: `CONFIRMED_ROOT_CAUSE` / `AZURE_BLOB_METADATA_QUERY_SHAPE`. The deployed code queried `metadata.sha256`, but Azure CLI returns the metadata map itself; the correct JMESPath is `sha256`. This was not evidence of missing IAM: Azure Portal read-back showed `worker-artifacts` and the container-level `Storage Blob Data Contributor` assignment for the deployment service principal.
* **Implementation**: the bounded helper from `6edcdbc6576ae9585f43ca6dc4fd2241262cc78e` centralizes probe, immutable upload/race handling, metadata read-back, and secret-safe diagnostics. The follow-up correction changes its metadata query to `--query sha256` and adds a regression that rejects the nested query. The application/package/Teams version remains `1.0.103`; no ZIP or app upload is justified by this CI-only fix.
* **Verification**: RED reproduced the nested query assertion; after the correction `node scripts/azure-worker-blob-stage-test.mjs`, `node scripts/azure-platform-contract-test.mjs`, and `node scripts/azure-core-test-runner-test.mjs` are GREEN.
